A search backend is a plain object satisfying the exported `SearchBackend` interface, passed as the
[`search`](/configuration/search/) option. `OpenSearchBackend` is one; your own is an object literal typed
`SearchBackend`.

```ts
interface SearchBackend {
  readonly capabilities: BackendSearchCapability;
  search(request: SearchRequest, context: RequestContext): Promise<SearchResult>;
  index(docs: SearchDocument[], options?: { tx?: unknown }): Promise<void>;
  remove(ids: string[]): Promise<void>;
}
```

The contract has no lifecycle methods: you own any client and its connections.

## `capabilities`

What `GET /capabilities` publishes as `search`, and the only thing arocapi validates requests against:

```ts
type BackendSearchCapability = {
  filters: Record<string, { type: 'string' | 'date' | 'number' | 'boolean'; label?: string }>;
  facets: Record<string, { label?: string }>;
  sorts: Record<string, { label?: string }>;
  searchTypes: { basic: {}; advanced?: { fields: Record<string, { label?: string }> } };
  geo: { supported: boolean };
};
```

`capabilitiesFromFields(fields)` derives it from [field declarations](/configuration/search/#fields), publishing only
fields with a role. You can also write it directly. `relevance` is always a sort and isn't listed.

## `search(request, context)`

arocapi validates and normalises the request first, so the backend only ever receives a valid one. An undeclared
filter key, sort or search type, a bad range, and geo parameters when `geo.supported` is false are a 400 before the
backend is called. `SearchRequest` has:

| Field              | Type                                          | Purpose                                                          |
| ------------------ | --------------------------------------------- | ---------------------------------------------------------------- |
| `searchType`       | `basic` or `advanced`                         | A declared search type.                                          |
| `query`            | string for `basic`, `AdvancedQuery` tree for `advanced` | A basic query is the raw text, for the backend to interpret its own way. |
| `filters.terms`    | `Record<string, string[]>`                    | Exact-term filters on `string` and `boolean` filters: any value within a field, every field. |
| `filters.ranges`   | `Record<string, { gte?, lte? }[]>`             | Inclusive range filters on `date` and `number` filters: any range within a field, every field. Date bounds are `Date`s (UTC instants), number bounds numbers. Exact values on these filters arrive here too, as ranges. |
| `boundingBox`      | `{ topRight, bottomLeft }`, optional          | Only when `geo.supported`. `bottomLeft.lng` above `topRight.lng` crosses the antimeridian. |
| `geohashPrecision` | integer, optional                             | Only when `geo.supported`, and always with `boundingBox`.        |
| `limit`, `offset`  | integers                                      | The page.                                                        |
| `sort`, `order`    | a declared sort or `relevance`; `asc` or `desc` | `relevance` is best match first, stable across pages for an empty query. |
| `visibility`       | `SearchVisibilityWhere`, the [search visibility filter](/configuration/visibility/#searchvisibilityfilter)'s result | Already resolved, so the backend never calls consumer code. Not yet checked. |

An advanced query arrives already parsed and checked against the declared advanced fields and the
[caps](/reference/search-queries/#caps), as an `AdvancedQuery`:

```ts
type AdvancedQuery =
  | { type: 'and' | 'or'; clauses: AdvancedQuery[] }
  | { type: 'not'; clause: AdvancedQuery } // everything the clause doesn't match
  | { type: 'match'; field: string; value: string; phrase: boolean }
  | { type: 'all' }; // an empty query
```

A `match` on a `text` field matches all the words of `value`, or the exact phrase if `phrase`; on any other type it
matches `value` exactly.

`context` is the request context, `{ request, fastify }`.

The backend checks `visibility` against its fields on every search, since only it knows the fields with no role. On an
undeclared field, an operator that doesn't fit the field's type or a bad value, it throws a plain `Error` naming the
field, which arocapi answers with a 500 and logs. It applies `visibility` to the hits, the total and the facets, with
the [semantics](/configuration/visibility/#semantics) every backend shares, and returns a `SearchResult`:

```ts
type SearchResult = {
  total: number; // exact
  hits: { id: string; searchExtra?: { score?: number; highlight?: Record<string, string[]> } }[]; // ordered
  facets?: Record<string, { name: string; count: number }[]>;
  geohashGrid?: Record<string, number>;
};
```

Facet buckets are named by the value as a string and ordered by count, then name. A `date` facet has one bucket per
UTC year with matches, named `"YYYY"` and ordered by year. `geohashGrid` counts the hits in the box per geohash at
`geohashPrecision`. arocapi then:

- loads each hit's Record from the database under `entityVisibilityFilter`, dropping (and logging) any it can't load;
- attaches `access`, runs the entity transformers and passes `searchExtra` through unchanged;
- fills in an empty list for any declared facet the backend left out;
- reports the time spent in `search` as `searchTime`.

### Errors

Throw the exported `SearchQueryError` for a query you can't run, including your engine's own limits. arocapi answers
422 `VALIDATION_ERROR` with its message. Any other error is a 500, logged with the real error.

## `index(docs, options?)` and `remove(ids)`

`index` upserts a batch of [search documents](/configuration/search/#search-documents) idempotently, and `remove` is
idempotent. Each entity must exist in the database before its document is indexed; a hit whose entity doesn't exist
is dropped from results. `options.tx` is for a backend that writes inside the consumer's database transaction. A
read-only backend throws from both.
