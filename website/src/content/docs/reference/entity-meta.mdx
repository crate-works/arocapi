The `Entity` and `File` models (see [Entities & hierarchy](/concepts/entities/)) each have a nullable JSON column,
`meta`, for your own data. arocapi never puts `meta` in
an API response, so it can hold storage locations and internal flags.

| Column        | Passed to                                                             | Typical use                              |
| ------------- | --------------------------------------------------------------------- | ---------------------------------------- |
| `Entity.meta` | both [storage](/configuration/storage/) halves, and your [`entityVisibilityFilter`](/configuration/visibility/#entityvisibilityfilter) can query it | Where the RO-Crate metadata is stored; visibility flags such as drafts. |
| `File.meta`   | the storage backend's [`content`](/configuration/storage/#the-halves) half | Where the file's bytes are stored.       |

`meta` is typed as Prisma's `JsonValue`, so narrow it before reading fields.

## Storage keys

Each reference storage backend reads a default Storage key from `meta`, unless you supply its `locate` option. Write
these keys when you index:

| Backend                                               | Content                 | Metadata                  | Override                                     |
| ----------------------------------------------------- | ----------------------- | ------------------------- | -------------------------------------------- |
| [`DirectoryStorage`](/configuration/storage/#directorystorage) | `File.meta.storagePath` | `Entity.meta.storagePath` | `locate.content(file, entity)`, `locate.metadata(entity)` |
| [`EntityMetaMetadata`](/configuration/storage/#entitymetametadata) | none (Metadata only) | `Entity.meta.rocrate`, the RO-Crate metadata object itself | `key` |
| [`S3Storage`](/configuration/storage/#s3storage)       | `File.meta.storageKey`  | `Entity.meta.storageKey`  | `locate.content(file, entity)`, `locate.metadata(entity)` |
| [`OcflStorage`](/configuration/storage/#ocflstorage) | `File.meta.ocflObject` + `File.meta.ocflPath` | `Entity.meta.ocflObject` + `Entity.meta.ocflPath` (default `ro-crate-metadata.json`) | `locate.content(file, entity)`, `locate.metadata(entity)`, returning `{ object, path }` |

Keys are relative to the backend's root or bucket. An absent key is a 404. A key that isn't a string, `null`
included, or that is absolute or has a `..` segment, is a 500. `EntityMetaMetadata` reads no key: the value is the
Metadata, and one that isn't a JSON object is a 500. OCFL keys are an object id, which the storage layout maps and
isn't checked for `..`, and a logical path inside its head version, not a path on disk. The root exports a TypeScript
type for each shape, such as `DirectoryStorageMeta`:

## Visibility flags

A flag in `Entity.meta` can drive the [visibility filters](/configuration/visibility/). Mirror it into your search
documents as a declared field with no role, for example `draft: { type: 'boolean' }`, so the search filter can match
the same entities. In Prisma, a plain `not` on a
JSON path also excludes rows where `meta` or the path is null, so match those explicitly:

`Prisma` here is the namespace from your generated Prisma client. JSON path filters can't use arocapi's indexes; for
large repositories, store visibility flags in your own indexed columns.
