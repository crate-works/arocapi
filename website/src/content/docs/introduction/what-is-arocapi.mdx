arocapi is a library that implements the [RO-Crate API](https://ro-crate-api.crate-works.org) specification, and part
of [CrateWorks](/introduction/crate-works/). It is a [Fastify](https://fastify.dev) plugin, so you register it in your
own app, and it adds routes for listing, searching and reading the
[entities](/concepts/entities/) in a repository: collections, objects and files, each described by RO-Crate metadata.

It is built for long-term archival repositories that follow the [PILARS](/introduction/pilars/) protocols. arocapi
owns the API and leaves the decisions that differ between repositories to you:

- **Where things live.** Entities are indexed in a database through Prisma and searched through a
  [search backend](/strategies/search/) such as OpenSearch. A storage backend, such as the built-in
  `DirectoryStorage` or your own, delivers RO-Crate metadata and file bytes from [your storage](/strategies/storage/). For now you fill the database and index yourself; support for the RO-Crate
  API's deposit routes, which will let you load RO-Crates through the API, is coming soon.
- **Who sees what.** Visibility filters decide which entities exist for a request. An access function decides
  whether a request may read an entity's full metadata and its file content, usually by
  [licence](/concepts/licences/). See [Visibility vs Access](/concepts/visibility-vs-access/).
- **What responses look like.** Transformers can add fields to every entity and file the API returns.

## How a request is handled

Every request passes the same checks in the same order, and your code runs at each step. The
[request lifecycle](/concepts/request-lifecycle/) covers it in detail. An entity Hidden from a
request doesn't exist as far as that request is concerned. Its Record appears in listings, search and entity
responses whenever it is Visible, but reading its Metadata or a file's Content also needs access.
[Record, Metadata, Content](/concepts/record-metadata-content/) describes these levels, and
[Visibility vs Access](/concepts/visibility-vs-access/) shows what each route returns.

```mermaid
flowchart LR
  request[Request] --> visible{Visible?}
  visible -- no --> notFound[404, or 401 to prompt a login]
  visible -- yes --> route{Route}
  route -- listing, search or entity --> transformers[Your transformers]
  transformers --> record[Record with its access]
  route -- metadata or file --> accessible{Accessible?}
  accessible -- no --> refused[401 or 403]
  accessible -- yes --> storage[Your storage backend]
  storage --> bytes[Metadata or file content]
```

To set up your own, start with [Install](/getting-started/install/).
