`GET` and `HEAD /entity/:id/metadata` and `/file/:id` go through a storage backend. arocapi calls it only after the
entity is Visible and the request has access, so it doesn't need its own checks (see the [request
lifecycle](/concepts/request-lifecycle/#metadata-and-content-routes)). arocapi ships
[`DirectoryStorage`](#directorystorage), the Metadata half [`EntityMetaMetadata`](#entitymetametadata),
[`S3Storage`](#s3storage) and [`OcflStorage`](#ocflstorage), or you can [write your own](/reference/storage-backend/).
[Storage](/strategies/storage/) compares ways to serve bytes.

| Option    | Required | Type             | Default | Purpose                                                    |
| --------- | -------- | ---------------- | ------- | ---------------------------------------------------------- |
| `storage` | yes      | `StorageBackend` | none    | Delivers an entity's Metadata and a file's Content.        |

Registration throws `storage is required` without it, and `storage.metadata is required` or
`storage.content is required` without either half.

## The halves

A storage backend is a plain object of two halves, `{ metadata, content }`:

| Half       | Serves                             | Receives                                                                |
| ---------- | ---------------------------------- | ----------------------------------------------------------------------- |
| `metadata` | `GET`, `HEAD /entity/:id/metadata` | the `Entity` row, including `entity.meta`, and the request context      |
| `content`  | `GET`, `HEAD /file/:id`            | the `File` row and its file entity, both with `meta`, and the request context with `contentDisposition` |

Each returns a [delivery](/reference/storage-backend/#deliveries), or `null` for a 404, and may be async. `HEAD` and
`GET` make the same call, so their headers always agree. The `meta` columns hold what a backend needs to find the
bytes; see [Entity meta](/reference/entity-meta/#storage-keys).

## `DirectoryStorage`

Serves both halves from files below a directory. Import it from `arocapi/storage/directory`:

<Code code={storageDirectory} lang="ts" />

| Option   | Required | Type                      | Default                 | Purpose                                         |
| -------- | -------- | ------------------------- | ----------------------- | ----------------------------------------------- |
| `root`   | yes      | string                    | none                    | The directory every Storage key is relative to. |
| `locate` | no       | `{ metadata?, content? }` | read `meta.storagePath` | Where each item sits below `root`: `metadata(entity)` and `content(file, entity)` return, or resolve to, a relative path or `null`. |

Without `locate`, Metadata is read from `Entity.meta.storagePath` and Content from `File.meta.storagePath`. A Metadata
key names the RO-Crate metadata file itself, so several entities can share one.

- A missing key, a `locate` returning `null`, or no file at the path is a 404.
- A `storagePath` that isn't a string, `null` included, is a 500, logged with the entity id and key.
- A key that is absolute or has a `..` segment is a 500, before anything is read. An absolute `storagePath` written
  for arocapi 4 fails this way rather than being read as relative.

Content-Length and Last-Modified come from the file, with a weak ETag from its size and modification time.
Content-Type comes from `File.mediaType`; Metadata is always `application/ld+json`.

## `EntityMetaMetadata`

A Metadata half only, for RO-Crate metadata kept in the database: it serves the JSON object at a key in `Entity.meta`.
Pair it with another source's `content`, as in [Mixing sources](#mixing-sources). Import it from
`arocapi/storage/entity-meta`:

<Code code={storageEntityMeta} lang="ts" />

| Option | Required | Type   | Default   | Purpose                                                 |
| ------ | -------- | ------ | --------- | ------------------------------------------------------- |
| `key`  | no       | string | `rocrate` | The key in `Entity.meta` holding the RO-Crate metadata. |

- A missing key is a 404.
- A value that isn't a JSON object (a string, array, number, boolean or `null`) is a 500, logged with the entity id and
  key, so an indexing bug isn't served as Metadata.

arocapi serialises the object once, with its Content-Length and a strong ETag from those bytes, and no Last-Modified.
PostgreSQL stores `meta` as `jsonb`, so key order and whitespace aren't kept from what you wrote.

## `S3Storage`

Serves both halves from a bucket on any S3-compatible store, such as AWS S3, Cloudflare R2, Garage or VersityGW.
Import it from `arocapi/storage/s3`, and install its optional peer dependencies `@aws-sdk/client-s3` and
`@aws-sdk/s3-request-presigner`:

<Code code={storageS3} lang="ts" />

| Option      | Required | Type                      | Default                | Purpose                                                       |
| ----------- | -------- | ------------------------- | ---------------------- | ------------------------------------------------------------- |
| `client`    | yes      | `S3Client`                | none                   | Your client. You configure its credentials and endpoint, and destroy it at shutdown. |
| `bucket`    | yes      | string                    | none                   | The bucket every Storage key is relative to.                  |
| `locate`    | no       | `{ metadata?, content? }` | read `meta.storageKey` | Where each item sits in the bucket: `metadata(entity)` and `content(file, entity)` return, or resolve to, a key or `null`. |
| `delivery`  | no       | `'redirect'` or `'stream'` | `'redirect'`          | How Content reaches the client. Metadata always streams.      |
| `expiresIn` | no       | number                    | `300`                  | Seconds a presigned Content URL stays valid.                  |

Without `locate`, Metadata is read from `Entity.meta.storageKey` and Content from `File.meta.storageKey`.

- **`redirect`** answers `/file/:id` with a 302 to a presigned `GetObject` URL, for `HEAD` as well as `GET`. The URL
  makes the bucket answer with Content-Type from `File.mediaType` and the request's Content-Disposition, so
  `?disposition` and `?filename` still apply. Presigning makes no request, so a missing object is only found when the
  client follows the URL. The URL bypasses access until it expires, so keep `expiresIn` short; a download only has to
  start within it. A browser on another origin needs CORS on the bucket, or `?noRedirect=true`.
- **`stream`** proxies the bytes through arocapi, so clients never reach the bucket. Metadata is always served this
  way. arocapi reads Content-Length, ETag and Last-Modified with `HeadObject`, then fetches that same version with
  `GetObject` and `If-Match`; an object replaced in between is a 500 rather than a mix of two versions.

A missing key, a `locate` returning `null`, or no object at the key (on `stream`, and for Metadata) is a 404. A
`storageKey` that isn't a string (`null` included), or a key that is absolute or has a `..` segment, is a 500 before any request or
presign. Any other error from the store is a logged 500.

S3 answers a missing key with 403, not 404, unless the credentials allow `s3:ListBucket` on the bucket, so grant it
for missing objects to be 404s.

## `OcflStorage`

Serves both halves from the head version of objects in an [OCFL](https://ocfl.io) storage root on local disk, through
[`@ocfl/ocfl-fs`](https://www.npmjs.com/package/@ocfl/ocfl-fs). Install it alongside arocapi (`pnpm add
@ocfl/ocfl-fs`); it is an optional peer dependency, loaded only by `arocapi/storage/ocfl`. `@ocfl/ocfl-fs` is
licensed GPL-3.0-or-later: the licence applies to your app if you use this backend and distribute it.

`OcflStorage` is async, because it reads the storage root at startup:

<Code code={storageOcfl} lang="ts" />

| Option       | Required | Type                      | Default                                 | Purpose                                         |
| ------------ | -------- | ------------------------- | --------------------------------------- | ----------------------------------------------- |
| `root`       | yes      | string                    | none                                    | The OCFL storage root.                          |
| `objectRoot` | no       | `(id) => string`          | the layout in `ocfl_layout.json`        | Where an object sits, relative to `root`; may be async. |
| `locate`     | no       | `{ metadata?, content? }` | read `meta.ocflObject` and `meta.ocflPath` | Where each item is: `metadata(entity)` and `content(file, entity)` return, or resolve to, an `OcflLocation` `{ object, path }` or `null`. |

At startup `OcflStorage` reads `ocfl_layout.json` and its extension config (`extensions/<layout>/config.json`, such
as the digest algorithm and tuple size and number), and implements these storage layouts:

- [`0002-flat-direct-storage-layout`](https://ocfl.github.io/extensions/0002-flat-direct-storage-layout.html)
- [`0003-hash-and-id-n-tuple-storage-layout`](https://ocfl.github.io/extensions/0003-hash-and-id-n-tuple-storage-layout.html)
- [`0004-hashed-n-tuple-storage-layout`](https://ocfl.github.io/extensions/0004-hashed-n-tuple-storage-layout.html),
  including `shortObjectRoot`
- LDaCA's `000N-path-direct-storage-layout`

For any other layout, or a root without `ocfl_layout.json`, pass `objectRoot`, or it throws. It also throws if `root`
isn't an OCFL storage root.

Without `locate`, Metadata is read from `Entity.meta.ocflObject` and `Entity.meta.ocflPath`, which defaults to
`ro-crate-metadata.json`, and Content from `File.meta.ocflObject` and `File.meta.ocflPath`. `object` is the OCFL
object id and `path` a logical path in the object's head version.

- Each request loads the object's inventory, with no cache, and serves the head version. Older versions and a
  mutable HEAD (extension 0005) are never served.
- A missing key, a `locate` returning `null`, an object that doesn't exist or a logical path not in head is a 404.
- An `ocflObject` or `ocflPath` that isn't a string, `null` included, is a 500, logged with the entity id and key, as
  is a logical path that is absolute or has a `..` segment. An object id is any string, mapped by the storage layout.
- An inventory that fails its sidecar digest check or won't parse is a 500, as is an object root outside the storage
  root, or a manifest path outside its object or not naming a file. A request made while a writer swaps an inventory may also get a 500.

Content-Length and Last-Modified come from the file on disk, with a strong ETag from its inventory digest.
Content-Type comes from `File.mediaType`; Metadata is always `application/ld+json`.

## Query parameters

`/file/:id` accepts, on `GET` and `HEAD`:

| Parameter     | Values                   | Default         | Effect                                                       |
| ------------- | ------------------------ | --------------- | ------------------------------------------------------------ |
| `disposition` | `inline` or `attachment` | `inline`        | `Content-Disposition` type.                                  |
| `filename`    | string                   | `file.filename` | Filename in `Content-Disposition`.                           |
| `noRedirect`  | `true` or `false`        | `false`         | Answer a `redirect` delivery with 200 `{ "location": url }`. |

arocapi sends `Content-Disposition` on `stream` and `path` deliveries, and passes the same value to `content` as
`contentDisposition`, so a redirecting backend can bake it into its URL. Any other `disposition` or `noRedirect` value
is a 400. `/entity/:id/metadata` takes no query parameters.

## Range requests

arocapi doesn't handle `Range` headers yet: a `stream` or `path` delivery is always sent whole, with the full
`Content-Length`. A redirect to storage that seeks, such as a presigned object storage URL, supports ranges today, and
`path` deliveries will once [Range support](https://github.com/crate-works/arocapi/issues/45) lands.
